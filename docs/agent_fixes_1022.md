## 2. 문제별 원인

### A. 범위 검색 누락 (검색 버그)
- 벡터 검색은 `WHERE file_name = ANY(범위) ORDER BY embedding <=> 질의 LIMIT 8`이다. pgvector HNSW 인덱스는 전체 문서에서 근접 후보 약 40개(`ef_search`)를 먼저 뽑은 뒤 조건으로 거른다. 그래서 후보 40개에 범위 안 문서가 없으면 결과가 비어 버린다.
- 실제 DB에서 재현한 결과(무작위 청크 300개를 질의로 사용):

| 범위 | 파일 수 | 8개 미만 | 0건 |
|---|---:|---:|---:|
| 기본·negative (용어집+약관) | 16 | 0 | 0 |
| 금융생활 (가이드북) | 1 | 0 | 0 |
| **추가 PDF** | 6 | **138** | **134** |

  가이드북은 DB가 인덱스를 쓰지 않는 계획을 골라 문제가 없었고, 추가 PDF만 인덱스를 썼다.
- 실행 기록에서도 확인했다. ADD-IN06은 첫 검색에서 parent 0개, ADD-SE13은 1개를 받았다.
- 검색 평가(`scripts/eval_retrieval.py`)는 범위 필터 없이 검색하므로 이 버그의 영향이 없었다. 수정 후 다시 돌려도 수치가 같다(Vector MRR 0.885). 따라서 **검색 평가는 실제 Agent 조건(범위 필터 있음)을 반영하지 못했다.**
- 수정: 질의마다 `SET LOCAL enable_indexscan = off`로 정확 검색을 한다. 청크가 3,041개라 질의당 약 10ms로 인덱스와 속도가 같고, 누락은 0건이 된다. `hnsw.iterative_scan = strict_order`도 누락은 없앴지만 정확 검색과 순위가 63/100만 같았다.

### B. 문맥 상한과 선착순 누적
- Agent는 parent를 최대 8개 누적한다. 첫 검색이 보통 5개를 채우므로 재검색 결과는 3자리에만 들어가고, 3번째 검색에서는 자리가 없다.
- 평가 Agent가 `relevant_docs`(실제로 쓸 문서 번호)를 내지만 코드가 쓰지 않았다. 평균 1.6개만 관련 있다고 판정됐는데 4.8개를 계속 들고 갔다.
- 재검색한 22문항의 라운드별 기록:
  - 문맥이 이미 8개라 새 문서 0개인 라운드가 9문항(ADD-HF15, ADD-IN15, ADD-RP06, NEG003, NEG052, POS051, POS059, POS088, POS097)에서 나왔다.
  - 그 라운드에도 피드백·개선·평가 LLM 호출 3회가 그대로 나갔다.
- 수정: 재검색 전에 `relevant_docs`의 문서만 남기고(번호도 1부터 다시 매김), 버린 문서는 다시 들이지 않는다. 트레이스에 `pruned_parents`로 기록한다.

### C. 종료 조건 순서
- 기존 `stop_reason`은 평가 LLM을 다시 부른 **뒤에** "새 parent 0개"를 확인했고, 3번째 라운드에서는 `max_rounds`가 먼저 걸렸다. 그 결과 `no_new_evidence`는 270문항에서 한 번도 나오지 않았다.
- 수정: 검색 노드가 새 parent 0개를 감지하면 `stop_reason=no_new_evidence`를 남기고, 그래프가 평가를 건너뛰어 바로 답변으로 간다.

### D. 응답 유형 판단이 두 곳에 나뉨
- 보류 판단은 평가 단계(판정)와 답변 단계(`response_type`) 두 곳에서 일어나고, 답변 Agent가 평가 판정을 뒤집을 수 있었다. P2 시도 3번이 순이득 없이 끝난 것도 한 곳의 문구만 고쳤기 때문이다.
- 답변 프롬프트의 "재검색이 끝났다(stop_reason=max_rounds)는 이유만으로 abstain을 고르지 않습니다"가 근거가 없을수록 `answer` 쪽으로 밀었다. ADD-HF15, IN15, SE15, POS090이 모두 `max_rounds` 뒤 `answer`로 틀렸다.
- 수정:
  - 답변 출력에 `core_answered`(질문의 중심 물음에 문서 근거로 답했는가)를 추가했다.
  - 응답 유형은 코드(`decide_type`)가 정한다. `answer`·`correct`인데 `core_answered=false`면 `abstain`으로 바꾸고, 평가가 `inappropriate`이면 `refuse`, `ambiguous`이면 `clarify`로 고정한다. 평가가 대체 경로(degraded)일 때는 고정하지 않는다.
  - 위 프롬프트 문장은 삭제했다.
  - 코드가 유형을 바꾸면 트레이스에 `type_override`로 남긴다.
- 보정(`20d82a6`): 처음에는 `out_of_scope`도 `abstain`으로 고정했다. 그러자 다중 질문의 일부만 없는 POS051·POS079와 평가가 `out_of_scope`로 오판한 POS088이 과보류됐다(38문항 실행 `103438`). 그래서 `out_of_scope` 고정을 빼고 `core_answered` 설명을 "하위 질문 일부만 없으면 true"로 명확히 했다. 보정 후 POS051·POS079는 복구됐고 POS088은 여전히 `abstain`이다.

### 해석
- **정확성(답변 내용)은 오르지 않았다.** A~D는 검색 누락, 문맥 관리, 종료 조건, 응답 유형을 고쳤고 답변 내용 자체는 건드리지 않았다. 실패의 약 68%를 차지하는 "내용 불완전"은 그대로다.
- **38문항 테스트(엄격 0.66~0.71 → 0.84)는 효과를 과대평가했다.** 기준선에서 실패한 문항을 골라 실험했기 때문에, 원래 잘 되던 문항에서 생긴 부작용이 보이지 않았다.
- **의도한 효과는 났다.**
  - 답할 수 없는 질문에 답하는 경우가 실행당 6.7 → 2.0건으로 줄었다(팀 세트 엄격 +0.056).
  - 헛된 재검색이 줄어 토큰 -4%, 시간 -6%다.
- **같은 크기의 부작용이 생겼다.** 기준선 3회 중 과반에서 맞던 문항 12개가 틀렸다. 내역은 다음과 같다.
  - **`answer`↔`correct` 라벨만 바뀜 6개** (ADD-HF07, HP10, SE05, SE09, POS038, POS062): 완화 기준으로는 통과한다. 기존에도 실행마다 흔들리던 라벨이다.
  - **과보류 3개** (POS003, POS088, ADD-HF09): 평가가 `out_of_scope`·`insufficient`로 오판했다.
  - **P3-b 평가 문구의 영향 3개**: NEG023은 `refuse` → `abstain`, NEG032는 정정 → `refuse`, NEG009는 `abstain` → `clarify`로 바뀌었다.
- **D의 `core_answered` 강제 전환은 이득이 없었다.** 3회 실행에서 `answer → abstain` 전환이 5번 일어났고, 그중 맞은 것은 1번이다. 답할 수 없는 질문을 보류하게 된 것은 대부분 강제 전환이 아니라, 답변 프롬프트에서 "재검색 소진만으로 abstain 금지" 문장을 지운 효과로 보인다.

1. **D의 강제 전환 정리 (작은 수정, 바로 가능)**
   - `answer → abstain` 강제 전환(`core_answered=false`)은 5번 중 4번이 틀렸으므로 끈다. `core_answered`는 기록용으로만 남긴다.
   - 평가 프롬프트의 P3-b 문장 "대상이 특정된 질문에서 직접 묻는 값이 문서에 없으면 out_of_scope"가 과보류(POS088, ADD-HF09)와 NEG023의 원인 후보다. 이 문장만 빼고 비교한다.
2. **다중 근거 질문 분해 검색 (검색 누락 24~26건)**
   - 실패 문항이 모두 근거 2개 이상인 질문이다. 첫 검색 전에 질문을 하위 질문 2~3개로 나눠 각각 검색하고, 결과를 합친다.
   - 지금은 평가가 `sufficient`로 판정해 재검색이 일어나지 않으므로, 재검색 규칙으로는 이 문항들을 잡지 못한다.
   - 비용은 LLM 호출 1회와 검색 몇 회가 늘어난다. 대안으로 `child_k` 8→12, `max_parents` 5→7(잘림 3건 대응)을 먼저 비교할 수도 있다.
3. **답변 후 누락 점검 단계 (내용 불완전 84~94건)**
   - 프롬프트에 지시 한 줄을 넣는 방식(P1)은 효과가 없었다. 대신 답변 뒤에 점검 노드를 둔다. 점검 노드는 질문·문서·답변을 받아, 문서에 있는데 답변에 빠진 조건·예외·주의 문구를 목록으로 내고, 그 목록으로 답변을 보완한다.
   - LLM 호출이 1회 늘어나므로, 근거가 여러 개이거나 문서에 "다만·단·제외" 같은 단서 표현이 있는 문항에만 적용해 비용을 줄인다.
4. **평가 쪽 정리 (시스템 변경 아님)**
   - `answer`와 `correct`의 구분이 실행마다 흔들려(부작용 12개 중 6개) 엄격 점수 변화의 절반이 라벨 소음이다. 완화 점수를 주 지표로 쓰거나 해당 문항의 허용 유형을 정리한다.
   - 내용 불완전 문항 중 상당수는 부가 항목만 빠진 경우다(만점 0.586 vs 핵심 기준 보정 0.774). Judge 사람 보정과 핵심/부가 항목 검토를 마쳐야 3번의 효과를 제대로 잴 수 있다.

변경은 한 번에 하나씩 하고, 270문항 3회(병렬 약 10분, Judge 포함 약 20분)로 비교한다.

### 해석
- **정확성은 개선 3(답변 규칙)에서 크게 올랐다.** Judge 정확성 0.800 → 0.864(+0.064), 만점 비율 0.609 → 0.737이다. 실패의 2/3를 차지하던 "내용 불완전"을 겨냥한 것이 맞았다. 3회 범위(0.002~0.007)를 크게 넘는다.
  - 프롬프트에 지시 한 줄을 넣은 한용님의 P1 시도는 효과가 없었다. 반면 이번 변경은 답변 전에 **질문 요소 점검표(`question_parts`)를 출력 구조로 강제**한다. 이 차이가 결과를 가른 것으로 본다.

- **엄격 점수 하락은 라벨 문제다.**
  - `answer`가 기대인 196문항 중 `correct`로 붙인 수가 실행당 32 → 65(3a) → 90(3b)으로 늘었다. 점검표 규칙의 "질문 속 오해도 하나의 요소로 둔다"가 정정 라벨을 늘린 것으로 보인다.

### 남은 과제
1. **라벨 정리**: `answer`/`correct` 구분 규칙을 답변 프롬프트에 명시하거나(질문에 사실과 다른 전제가 있을 때만 `correct`), 채점에서 완화 점수를 주 지표로 둔다.
2. **개선 2 비용 줄이기**: 분해가 필요한 질문에만 분해 호출을 하도록 조건을 걸거나(예: 질문 길이·접속어), 분해 검색어의 parent 수를 줄인다. 효과가 비용 대비 작으면 되돌리는 것도 선택지다.
3. **Judge 사람 보정**: 점수가 크게 오른 만큼, 표본 30문항으로 Judge가 사람 판단과 맞는지 확인한다.
4. **정원하 브랜치와 병합**: 개선 3은 그 브랜치의 v4·v5·v7을 옮긴 것이라, 병합 시 `rag/multi_agent.py` 충돌을 이 버전 기준으로 정리하면 된다.
