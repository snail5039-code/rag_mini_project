## 2. 문제별 원인

### A. 범위 검색 누락 (검색 버그)
- 벡터 검색은 `WHERE file_name = ANY(범위) ORDER BY embedding <=> 질의 LIMIT 8`이다. pgvector HNSW 인덱스는 전체 문서에서 근접 후보 약 40개(`ef_search`)를 먼저 뽑은 뒤 조건으로 거른다. 그래서 후보 40개에 범위 안 문서가 없으면 결과가 비어 버린다.
- 실제 DB에서 재현한 결과(무작위 청크 300개를 질의로 사용):

| 범위 | 파일 수 | 8개 미만 | 0건 |
|---|---:|---:|---:|
| 기본·negative (용어집+약관) | 16 | 0 | 0 |
| 금융생활 (가이드북) | 1 | 0 | 0 |
| **추가 PDF** | 6 | **138** | **134** |

  가이드북은 DB가 인덱스를 쓰지 않는 계획을 골라 문제가 없었고, 추가 PDF만 인덱스를 썼다.
- 실행 기록에서도 확인했다. ADD-IN06은 첫 검색에서 parent 0개, ADD-SE13은 1개를 받았다.
- 검색 평가(`scripts/eval_retrieval.py`)는 범위 필터 없이 검색하므로 이 버그의 영향이 없었다. 수정 후 다시 돌려도 수치가 같다(Vector MRR 0.885). 따라서 **검색 평가는 실제 Agent 조건(범위 필터 있음)을 반영하지 못했다.**
- 수정: 질의마다 `SET LOCAL enable_indexscan = off`로 정확 검색을 한다. 청크가 3,041개라 질의당 약 10ms로 인덱스와 속도가 같고, 누락은 0건이 된다. `hnsw.iterative_scan = strict_order`도 누락은 없앴지만 정확 검색과 순위가 63/100만 같았다.

### B. 문맥 상한과 선착순 누적
- Agent는 parent를 최대 8개 누적한다. 첫 검색이 보통 5개를 채우므로 재검색 결과는 3자리에만 들어가고, 3번째 검색에서는 자리가 없다.
- 평가 Agent가 `relevant_docs`(실제로 쓸 문서 번호)를 내지만 코드가 쓰지 않았다. 평균 1.6개만 관련 있다고 판정됐는데 4.8개를 계속 들고 갔다.
- 재검색한 22문항의 라운드별 기록:
  - 문맥이 이미 8개라 새 문서 0개인 라운드가 9문항(ADD-HF15, ADD-IN15, ADD-RP06, NEG003, NEG052, POS051, POS059, POS088, POS097)에서 나왔다.
  - 그 라운드에도 피드백·개선·평가 LLM 호출 3회가 그대로 나갔다.
- 수정: 재검색 전에 `relevant_docs`의 문서만 남기고(번호도 1부터 다시 매김), 버린 문서는 다시 들이지 않는다. 트레이스에 `pruned_parents`로 기록한다.

### C. 종료 조건 순서
- 기존 `stop_reason`은 평가 LLM을 다시 부른 **뒤에** "새 parent 0개"를 확인했고, 3번째 라운드에서는 `max_rounds`가 먼저 걸렸다. 그 결과 `no_new_evidence`는 270문항에서 한 번도 나오지 않았다.
- 수정: 검색 노드가 새 parent 0개를 감지하면 `stop_reason=no_new_evidence`를 남기고, 그래프가 평가를 건너뛰어 바로 답변으로 간다.

### D. 응답 유형 판단이 두 곳에 나뉨
- 보류 판단은 평가 단계(판정)와 답변 단계(`response_type`) 두 곳에서 일어나고, 답변 Agent가 평가 판정을 뒤집을 수 있었다. P2 시도 3번이 순이득 없이 끝난 것도 한 곳의 문구만 고쳤기 때문이다.
- 답변 프롬프트의 "재검색이 끝났다(stop_reason=max_rounds)는 이유만으로 abstain을 고르지 않습니다"가 근거가 없을수록 `answer` 쪽으로 밀었다. ADD-HF15, IN15, SE15, POS090이 모두 `max_rounds` 뒤 `answer`로 틀렸다.
- 수정:
  - 답변 출력에 `core_answered`(질문의 중심 물음에 문서 근거로 답했는가)를 추가했다.
  - 응답 유형은 코드(`decide_type`)가 정한다. `answer`·`correct`인데 `core_answered=false`면 `abstain`으로 바꾸고, 평가가 `inappropriate`이면 `refuse`, `ambiguous`이면 `clarify`로 고정한다. 평가가 대체 경로(degraded)일 때는 고정하지 않는다.
  - 위 프롬프트 문장은 삭제했다.
  - 코드가 유형을 바꾸면 트레이스에 `type_override`로 남긴다.
- 보정(`20d82a6`): 처음에는 `out_of_scope`도 `abstain`으로 고정했다. 그러자 다중 질문의 일부만 없는 POS051·POS079와 평가가 `out_of_scope`로 오판한 POS088이 과보류됐다(38문항 실행 `103438`). 그래서 `out_of_scope` 고정을 빼고 `core_answered` 설명을 "하위 질문 일부만 없으면 true"로 명확히 했다. 보정 후 POS051·POS079는 복구됐고 POS088은 여전히 `abstain`이다.
