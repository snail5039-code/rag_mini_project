기준선 실행(기본 RAG `20261021_115125`, Multi-Agent `20261021_120715`, 각 270문항)의 저장된 결과만으로 다시 집계했다. 코드: `scripts/analysis/rescore_nonllm.py`, 원자료: `06_results/eval/rescore_nonllm.json`.

## C-2. 답할 수 없는 질문을 인용·문맥 지표에서 제외

기대 행동이 보류·거절·되묻기인 58문항(제공 30, 팀 28)은 올바르게 응답해도 인용이 없어서 인용 지표가 깎인다. 이를 빼고 답할 수 있는 212문항만으로 다시 계산했다.

| 지표 | 기본 RAG 전체 270 → 답할 수 있는 212 | Multi-Agent 270 → 212 |
|---|---|---|
| 인용 Hit (전체) | 0.885 → **0.948** | 0.960 → **0.995** |
| 인용 Hit (**팀 골든셋**) | 0.772 → **0.952** | 0.899 → **1.000** |
| 인용 Hit (제공 골든셋) | 0.946 → 0.946 | 0.993 → 0.993 |
| 인용 Recall (전체) | 0.810 → 0.867 | 0.882 → 0.913 |
| 인용 Recall (팀 골든셋) | 0.738 → 0.914 | 0.861 → 0.962 |
| 문맥 Recall (전체) | 0.916 → 0.920 | 0.935 → 0.936 |

- **팀 골든셋의 낮은 인용 점수는 거의 전부 측정 방식의 문제였다.** 답할 수 있는 팀 문항만 보면 Multi-Agent 인용 Hit는 1.000이다. 제공 골든셋은 보류 문항에 근거 ID가 비어 있어 영향이 없다.
- 이 보정은 한계점 3번(README)에 해당한다. 앞으로 인용·문맥 지표는 "답할 수 있는 문항 기준"을 함께 보고한다.

## C-3. 응답 유형 라벨 정리

| 지표 | 기본 RAG | Multi-Agent |
|---|---:|---:|
| 엄격 (기대한 유형과 정확히 같음) | 0.730 | 0.830 |
| 완화 (허용 유형이면 통과) | 0.941 | 0.959 |
| `answer`·`correct` 통합 | 0.941 | 0.959 |

- 완화 기준은 이미 `answer`와 `correct`를 서로 허용 유형으로 보므로 통합 기준과 값이 같다. 엄격과 완화의 차이(기본 0.21, MA 0.13)는 거의 `answer`와 `correct` 라벨이 바뀐 것이다.
- 따라서 **행동이 맞는지는 완화 기준을 대표 지표로 보고하고**, 엄격 기준은 참고로만 둔다. 앞서 본 실행 간 변동(`answer`↔`correct` 라벨 17~21건)이 엄격 지표의 흔들림이다.

## C-1. `must_include` 핵심/부가 분리와 재채점

`scripts/analysis/classify_must_include.py`(LLM `gemini-3.8-flash`)가 270문항의 `must_include` 항목 795개를 **핵심(core) 642개(81%)와 부가(extra) 153개(19%)**로 나눴다(`06_results/eval/must_include_core.json`, 항목마다 이유 포함). 기준은 "질문이 직접 묻는 결론·수치·조건·행동이면 핵심, 단서·한계·참고처럼 빠져도 핵심 답이 성립하면 부가"다. 이어서 저장된 Judge 결과의 항목별 충족 여부로 `scripts/analysis/rescore_core.py`가 다시 집계했다(시스템·Judge 재실행 없음, 결과 `rescore_core.json`).

| 지표 | 기본 RAG | Multi-Agent |
|---|---:|---:|
| Judge 정확성 만점 비율 (원래) | 0.567 | 0.589 |
| **정확성 만점 비율 (부가 항목만 빠진 문항을 만점으로 인정)** | **0.767** | **0.785** |
| 핵심 항목을 모두 충족한 문항 비율 | 0.748 | 0.778 |
| 핵심 항목 충족률 | 0.854 | 0.881 |
| 부가 항목 충족률 | 0.417 | 0.452 |
| 부가 항목 하나 때문에만 만점을 놓친 문항 | 54 | 53 |

| 세트별 (Multi-Agent) | 원래 → 보정 만점 비율 | 항목 중 부가 비율 |
|---|---|---|
| 제공 180 | 0.656 → **0.806** | 89 / 532 (17%) |
| 팀 90 | 0.456 → **0.744** | 64 / 263 (24%) |

- **점수가 낮게 보인 가장 큰 이유가 확인됐다.** 정확성 만점 59%는 부가 항목을 하나 놓친 문항 53개(20%)를 포함한 값이고, 이를 만점으로 인정하면 **약 79%**다. 팀 골든셋은 45.6% → 74.4%로 크게 오른다.
- 팀 골든셋이 제공 세트보다 점수가 낮았던 이유도 일부 설명된다. 팀 `must_include`는 부가 항목 비율이 24%로 제공 세트(17%)보다 높다. 제가 만든 `must_include`가 부차 설명을 더 많이 요구했다.
- 모델은 핵심 항목은 88% 충족하고, 부가 항목은 45%만 담는다. 부가 항목을 빠뜨리는 경향은 사실이지만 핵심 정답은 대부분 맞게 쓴다.
- 보정 만점 비율 = Judge 정확성 2점이거나, 1점이면서 핵심 항목이 모두 충족되고 `must_not` 위반이 없는 문항이다. **추정치(상한에 가까움)**이며, 정확성 1점의 이유가 항목 누락이 아닌 경우는 구분하지 못한다.
- **한계**: 핵심/부가 분류는 LLM이 했고 사람이 검토하지 않았다. 표본을 보면 대체로 타당하나(예: 질문이 이미 전제한 배경 설명, 청약철회 후속 절차는 부가) "지체 없이"(POS035)나 "최신성 확인"(NEG034)처럼 핵심일 수 있는 항목이 부가로 분류된 사례가 있다. 사람 검토 후 분류를 고치고 다시 집계하면 된다.
