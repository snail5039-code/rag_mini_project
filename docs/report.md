# 실험 결과 보고서 — 청킹·검색·Multi-Agent RAG

담당 범위: 청킹·임베딩, 검색 평가, 기본 RAG·Multi-Agent RAG 구현과 개선 (정원하). 설계는 [pipeline.md](pipeline.md), 그래프 구조는 [agent_graph.md](agent_graph.md), 재현 방법은 [how_to_run.md](how_to_run.md)를 보세요.

## 요약

| | 기본 RAG | **최종 Multi-Agent (v7)** |
|---|---|---|
| 골든셋 90문항 Judge 정확성 (최종 성능, judge_v1 기준) | 0.694 | **0.794** |
| 골든셋 90문항 Judge 정확성 (완화 기준 judge_v2) | 0.917 | **0.961** |
| 　답할 수 있는 질문 / 답할 수 없는 질문 | 0.741 / 0.618 | 0.759 / **0.853** |
| 제공 180문항 Judge 정확성 (개발용, 2회) | 0.797 | 0.922 / 0.906 |
| 근거 충실성 (골든셋) | 0.989 | 0.989 |
| 문항당 모델 호출 · 토큰 · 시간 (골든셋) | 1.0회 · 3.1천 · 5.9초 | 2.7회 · 8.7천 · 18.0초 |

- **최종 설정:** Parent-Child 청킹, child Vector 검색, Multi-Agent(재검색 최대 2회), 답변 Agent에 질문 요소 점검표와 보류·되묻기 안내 규칙, 답변 모델 `gemini-3.7-flash`.
- **비용 대비 효과:** Multi-Agent는 비용이 약 2.8배, 시간이 약 3배 들고, 골든셋 정확성을 +0.10 올립니다. 개선의 대부분은 **답할 수 없는 질문**(보류·되묻기·거절)에서 나왔습니다(+0.24). 답할 수 있는 질문에서는 +0.02에 그칩니다.
- **환각:** 지어낸 내용(근거 충실성)은 처음부터 거의 없었습니다. 남은 오류는 대부분 **필요한 요소를 덜 말한 것**입니다.

## 1. 실험 설계

### 데이터

| 용도 | 데이터 | 비고 |
|---|---|---|
| 개발·튜닝 | 제공 180문항 (positive 140, negative 40) | 모든 설정 비교에 사용 |
| 최종 검증 | 팀 골든셋 90문항 (`feature/golden-set`, 답할 수 없는 질문 34개) | 튜닝에 쓰지 않음 (예외는 4장 참고) |

질문 세트별 검색 범위를 고정했습니다. 기본 세트(positive·negative)는 용어집+약관, 금융생활 세트는 가이드북, 추가 세트는 추가 PDF만 검색합니다.

### 고정 조건과 바꾼 요소
- **고정:** 질문 세트, 검색 대상 PDF, 임베딩 모델(`gemini-embedding-2`, 1536차원), 평가 방법.
- **한 번에 하나만 변경:** 실험마다 하나의 요소만 바꿨습니다. 실행 간 변동(같은 설정으로 다시 돌리면 Judge 정확성이 ±0.01~0.02 달라짐)이 있어서, 답변 실험은 **같은 설정을 2회 실행**해 두 번 모두 기존 범위를 넘을 때만 채택했습니다.

### 평가 지표

| 대상 | 지표 | 방법 |
|---|---|---|
| 검색 | Hit@k, Recall@k, Precision@k, nDCG@k, MRR | 코드. 정답은 기준 답안의 근거 ID(용어·조항·페이지). child 단계(검색기가 찾았나)와 parent 단계(답변 Agent가 받은 문맥에 있나)를 나눠 봄 |
| 답변 (1차) | 응답 유형 일치, 문맥·인용 근거 Recall | 코드 |
| 답변 (최종) | 정확성(0~2), 필수 항목 충족, 금지 내용 위반, 근거 충실성, 인용 적합성, 대응 적절성 | LLM Judge (`gemini-3.8-flash`, 팀 루브릭 `judge_v1`). 표에서는 0~1로 정규화 |
| 비용 | 문항당 모델 호출, 검색 호출, 입출력 토큰, 시간 | 실행 기록 |

### 실행 기록
- 모든 실행은 `run_id`(시각 + 파이프라인 + 태그)로 PostgreSQL(`rag_runs`, `rag_case_results`, `retrieval_eval_runs/cases`)과 `06_results/`에 저장했습니다.
- 각 실행의 설정(모델, 프롬프트 전문, 청킹·검색 설정)은 `rag_runs.params`와 `*.summary.json`에 함께 남겼습니다.

## 2. 청킹·검색 실험 (제공 positive 140문항)

### 2-1. 청킹 방식 × 검색기

| 청킹 | 검색기 | Hit@1 | Hit@5 | Recall@5 | nDCG@5 | MRR |
|---|---|---|---|---|---|---|
| **Parent-Child 300** | **Vector** | **0.821** | **0.993** | **0.840** | **0.794** | **0.885** |
| Parent-Child 300 | MMR (λ=0.7) | 0.821 | 0.964 | 0.829 | 0.788 | 0.885 |
| Parent-Child 300 | Hybrid (RRF 0.5:0.5) | 0.771 | 0.957 | 0.818 | 0.774 | 0.854 |
| Parent-Child 300 | BM25 (Kiwi) | 0.557 | 0.807 | 0.670 | 0.600 | 0.662 |
| Recursive 300 | Vector / Hybrid | 0.664 / 0.686 | 0.921 / 0.921 | 0.781 / 0.780 | 0.693 / 0.711 | 0.768 / 0.786 |
| Recursive 500 | Vector / Hybrid | 0.600 / 0.636 | 0.850 / 0.864 | 0.714 / 0.748 | 0.649 / 0.665 | 0.715 / 0.730 |
| Recursive 800 | Vector / Hybrid | 0.564 / 0.650 | 0.857 / 0.864 | 0.734 / 0.743 | 0.638 / 0.664 | 0.696 / 0.750 |
| Recursive 1000 | Vector / Hybrid | 0.579 / 0.600 | 0.829 / 0.843 | 0.694 / 0.742 | 0.613 / 0.650 | 0.684 / 0.707 |

- **청킹:** 문서 구조 단위의 Parent-Child가 모든 Recursive 설정보다 확실히 좋았습니다. Recursive는 청크가 작을수록 좋았습니다.
- **검색기:** Parent-Child에서는 Vector가 가장 좋았습니다. Hybrid는 Recursive에서만 약간 도움이 됐습니다.
- **parent 단계:** Vector 기준 parent Recall@5는 0.901입니다. 답변 Agent가 받는 문맥은 평균 4.1천 자입니다.

### 2-2. 질문 유형별 검색 (가설: 정확한 금융 용어에는 키워드 검색이 유리하다)

질문을 LLM으로 용어형(31개: 용어·제도명을 직접 물음)과 상황형(109개: 상황을 풀어 씀)으로 분류했습니다.

| 검색기 | 용어형 Hit@5 / Recall@5 | 상황형 Hit@5 / Recall@5 |
|---|---|---|
| BM25 | 0.935 / 0.866 | 0.771 / 0.614 |
| Hybrid | 0.968 / 0.935 | 0.954 / 0.784 |
| **Vector** | **1.000 / 0.935** | **0.991 / 0.813** |

- BM25는 용어형 질문에서 훨씬 낫습니다. 이 점에서 가설은 맞았습니다.
- 하지만 Vector가 용어형 질문도 이미 잘 찾아서, 섞어도 이득이 없었습니다.
- 질문의 78%가 상황형이라 Vector가 기준으로 맞습니다.

### 2-3. 문맥 보존: child 앞 제목 prefix

Parent-Child child의 임베딩 입력에서 `제목: {조항·용어·소제목}`만 빼고 같은 3,041개를 다시 임베딩해 비교했습니다(Vector).

| | Hit@1 | Hit@5 | Recall@5 | Recall@10 | nDCG@5 | MRR | parent Recall@5 |
|---|---|---|---|---|---|---|---|
| 제목 prefix 있음 (기준) | 0.821 | 0.993 | 0.840 | 0.911 | 0.794 | 0.885 | 0.901 |
| 제목 prefix 없음 | 0.807 | 0.993 | 0.850 | 0.932 | 0.794 | 0.875 | 0.910 |

- 차이가 문항 1~2개 수준이라 **제목 prefix는 검색 성능에 의미 있는 영향이 없었습니다.**
- 따라서 Parent-Child가 Recursive보다 나은 이유는 제목보다 **청크 경계를 조항·용어·소제목에 맞춘 것**에 있습니다.
- prefix는 추가 비용이 없고 Hit@1이 약간 높아서 그대로 둡니다.

### 2-4. 검색에서 남은 약점
- **근거가 여러 개 필요한 문항(75개)의 parent Recall@5는 0.814**입니다. 근거가 하나인 문항은 1.000입니다.
- 어려운 문항(advanced)일수록 낮습니다(0.809). 대부분 약관 조항 2~4개를 엮어야 하는 질문입니다.
- 이것이 Multi-Agent 재검색 루프를 둔 이유입니다.

### 각 실험의 근거

**v10·v11 — 답변 구성 규칙과 few-shot (모두 기각)**
- 남은 감점(부수 정보 누락)을 겨냥해 답변 구성을 강제하거나(v10) 기준 답안 수준의 예시를 보여 줬지만(v11), 둘 다 v7의 실행 간 변동 범위(0.906~0.922) 안에 머물렀습니다.
- **제공 세트에서 v7 이후 네 가지 실험(v8~v11)이 모두 0.90~0.925에 머물러, 프롬프트 조정으로 얻을 수 있는 개선은 거의 소진된 상태입니다.**

**v8·v9 — 골든셋 실패 원인을 겨냥한 개선 (모두 기각)**
- v8은 보고서 5장의 개선점 1~3번(기준일, 모호성, 근거 없는 단정)을 묶어 적용했습니다. 처음 채점에서는 근거 충실성이 0.92로 떨어졌는데, **채점 쪽 문제**였습니다. 답변 Agent에게 준 문서 기준일을 Judge 문맥에는 넣지 않아서, 답변이 인용한 실제 기준일을 Judge가 "문맥에 없는 숫자"로 감점했습니다. Judge에게도 같은 기준일을 보여 주도록 고쳐 다시 채점하니 v7과 차이가 없었습니다(0.911/0.906 대 0.922/0.906).
- v9는 개선점 4번입니다. 그런데 답변 Agent가 `answer`·`correct`로 답할 때는 점검표의 거의 모든 요소에 근거를 채워서, 재검색 조건이 한 번도 걸리지 않았습니다. 근거 없음 표시 26건 중 22건은 보류·거절 답변이었습니다. **남은 누락은 근거를 못 찾아서가 아니라, 찾은 근거의 부수 정보를 답에 넣지 않아서** 생깁니다.

**v4 — 질문 요소 점검표**
- v3에서 정확성이 만점이 아닌 positive 43~44문항을 분석했습니다. **약 75%가 근거 문서를 다 받고도 답변에서 요소를 빠뜨린 경우**였고, 검색 누락은 9~11문항이었습니다.
- 그래서 답하기 전에 질문을 요소로 나누고, 요소별 근거(조건·기한·예외·미이행 시 결과)를 먼저 적게 했습니다.

**v5 — 보류·되묻기 안내 규칙**
- v4에서 남은 감점 중 13~17문항이 "보류는 맞게 했지만 안내가 부족한" 경우였습니다.
- 그래서 보류·되묻기·거절 시 다음 세 가지를 반드시 적게 했습니다.
  - 빠진 정보 (상품명, 계약서류 수령일 등)
  - 문서로 확인할 수 없는 이유 (회사별 별첨, 기준일 이후 제도, 개인 정보 등)
  - 확인할 곳
- 비용 증가 없이 답할 수 없는 질문 점수가 0.75~0.78에서 0.90으로 올랐습니다.

**v6 — 답변 검토 Agent (기각)**
- 초안을 문서와 대조해 빠진 점을 보완하게 했습니다.
- 실제로 보완한 문항은 180개 중 20개뿐이었고, 보류 답변을 고쳐 쓰다가 점수가 떨어졌습니다.

**v7 — 답변 모델 교체**
- 답변 Agent만 바꾸고, 나머지 Agent는 3.6 Flash 그대로입니다.
- 채점 모델(3.8 Flash)은 자기 채점 편향 때문에 후보에서 뺐습니다.
- `gemini-pro-latest`는 실제로 이전 세대 프리뷰(3.1 Pro)로 연결되어 오히려 낮았습니다.

## 4. 최종 검증 (골든셋 90문항)

| | 정확성 | 완전 정답 | 필수 항목 | 답할 수 있는 | 답할 수 없는 | 금지 위반 | 호출 · 토큰 · 시간 |
|---|---|---|---|---|---|---|---|
| 기본 RAG | 0.694 | 0.422 | 0.701 | 0.741 | 0.618 | 0.011 | 1.0 · 3.1천 · 5.9초 |
| Multi-Agent v2 | 0.739 | 0.500 | 0.774 | 0.759 | 0.706 | 0.033 | 2.6 · 8.2천 · 15.3초 |
| Multi-Agent v4 | 0.772 | 0.556 | 0.799 | 0.768 | 0.779 | 0.022 | 2.6 · 8.4천 · 18.0초 |
| **Multi-Agent v7** | **0.794** | **0.600** | **0.830** | 0.759 | **0.853** | 0.033 | 2.7 · 8.7천 · 18.0초 |

- **문항 단위:** v7은 기본 RAG보다 24문항 좋아지고 6문항 나빠졌습니다. v4보다는 10문항 좋아지고 6문항 나빠졌습니다.
- **카테고리별 정확성 (기본 → v7):**
  - 문서에 없는 정보 질문: 0.75 → 0.96
  - 잘못된 전제: 0.50 → 0.83
  - 개인 맞춤 추천: 0.67 → 0.83
  - 별첨 빈칸: 0.50 → 0.75
  - 일반 질문(grounded_qa): 0.74 → 0.76 (거의 그대로)

### 해석과 한계
- **제공 세트의 개선이 골든셋에서는 일부만 이어졌습니다.** v4 → v7이 제공 세트에서는 +0.06이지만 골든셋에서는 +0.02입니다. 반복 튜닝에 쓴 제공 세트(와 그 기준 답안 문체)에 어느 정도 맞춰졌다는 신호입니다. **최종 성능은 골든셋 수치로 보고합니다.**
- **골든셋을 한 번 본 시점이 있습니다.** v2를 골든셋으로 돌렸을 때 답할 수 없는 질문에 답하는 문제가 보였고, 이것이 v3에서 답변 규칙을 되돌린 판단에 영향을 줬습니다. 그 뒤의 튜닝(v4~v7)은 제공 세트로만 했습니다.
- **채점 편향 가능성:** 답변 모델(3.7 Flash)과 채점 모델(3.8 Flash)이 같은 계열입니다.
- **금지 내용 위반이 3건 남았습니다.**
  - POS087: 문맥에 없는 소득 기준을 단정했습니다.
  - ADD-IN11: 2020년 예시 자료를 최신 기준처럼 설명했습니다.
  - NEG056: 프롬프트 인젝션(출처 삭제 요구)을 무시한다고 밝히지 않았고 출처를 빠뜨렸습니다.

### 완화 기준(judge_v2)으로 본 결과

팀 합의로 채점 기준을 완화한 judge_v2를 정의하고, 기본 RAG와 v7에 **똑같이** 적용했습니다. judge_v1 결과는 그대로 두고 나란히 보고합니다.

- **judge_v2 정의:** 질문이 직접 묻는 핵심에 정확히 답하고 대응 유형이 맞으면 2점. 부가 설명, 확인 권고, 질문이 묻지 않은 부수 수치가 빠진 것은 감점하지 않습니다. 핵심 요소 일부 누락은 1점, 핵심 오류·대응 유형 오류·금지 내용 주장은 0점입니다.
- 채점 모델(`gemini-3.8-flash`), 문맥, 질문·기준 답안은 judge_v1과 같고, 루브릭 문장만 다릅니다(`scripts/eval_judge.py --rubric judge_v2`).

### 보조 지표: 치명적 오류 없음

Judge 정확성 1점 이상이면서 금지 내용 위반이 없는 비율입니다. "틀리거나 해서는 안 될 말을 한 답변이 얼마나 적은가"를 봅니다. 평균 정확성과 다른 지표이며, 평균 정확성을 대신하지 않습니다.

### 원인별 개선점 (우선순위)

1~4번 중 1~3번은 v8, 4번은 v9로 실험했지만 제공 세트에서 효과가 없었습니다(3장 참고). 남은 방향은 6번입니다.

1. **문서 기준일·시점 판단 (ADD-PF15, ADD-IN11):** 문서 메타데이터에 기준일(약관의 "원문 기준일", 보고서 발행연도)을 넣어 문맥과 함께 주고, "기준일 이후의 일·현재 시점을 묻는 질문"을 평가 Agent가 따로 판정하게 합니다.
2. **모호성 판정 (NEG046, NEG013):** 평가 Agent가 "질문의 대상이 여러 문서·상품에 해당하는가"를 검색 결과로 점검하게 합니다. 예를 들어 상위 parent들이 서로 다른 약관에서 나오면 모호하다고 봅니다.
3. **근거 없는 단정 차단 (POS087):** 점검표의 요소별 근거가 "문서에 없음"인데 답변에 확정 표현이 있으면, 코드로 막거나 다시 생성합니다.
4. **다중 근거 검색 (근거 2개 이상인 문항의 parent Recall 0.81):** 점검표에서 "문서에 없음"으로 나온 요소를 검색어로 바로 재검색합니다. 지금은 재검색이 평가 Agent 판정에만 걸려 있습니다.
5. **비용 절감:** 재검색 없이 첫 검색으로 끝나는 문항이 166/180개(제공 세트 v7)입니다. 쉬운 질문은 평가 호출을 건너뛰는 경로를 두면 비용을 줄일 수 있습니다.
6. **부수 정보 누락 줄이기:** 남은 감점 대부분은 문맥에 있던 세부(증감률, 예외 조건, 확인 안내)를 답에서 뺀 것입니다. 답변 길이와 완전성은 맞바꾸는 관계라서, 사용자에게 필요한 세부의 기준을 팀이 정한 뒤 그 기준으로 답변 규칙과 루브릭을 함께 맞추는 것이 다음 단계입니다.
